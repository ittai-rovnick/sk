Geo Platform — Full System Design

Complete design document covering structure, DB schema, API, and implementation plan. Updated April 2026.

Section 1 — Structure Examples

Before reading the schema, here are concrete examples of how the data fits together. These show a real workspace and every table row that would exist for each node in the tree.

1.1 Workspace Tree

A workspace is the top-level org container. Inside it: folders (for organizing maps), maps (the main working unit), and inside each map: groups and layers. The tree below shows a complete example.

Workspace: "Israel Survey Org" │ ├── Folder: "Field Operations" ← folders table row, workspace_id = above │ ├── Map: "Northern Survey 2025" ← maps table row, folder_id = above │ │ ├── Group: "Base Layers" ← map_groups row, map_id = above │ │ │ ├── Layer: "Roads" ← map_layers row linking to layers table │ │ │ └── Layer: "Topography" ← map_layers row │ │ ├── Group: "Survey Data" ← map_groups row │ │ │ ├── Layer: "Survey Points" ← map_layers row │ │ │ └── Layer: "Boundaries" ← map_layers row │ │ └── Layer: "Satellite Imagery" ← map_layers row, group_id = NULL (top-level in map) │ │ │ └── Map: "Southern Survey 2025" ← maps table row │ └── Embedded Map: "Shared Base" ← map_groups row with embedded_map_id set │ ├── Layer: "Roads" ← resolved at query time from the embedded map │ └── Layer: "Topography" ← resolved at query time from the embedded map │ ├── Folder: "Analysis" ← folders row │ └── Map: "Heat Analysis" ← maps row │ └── Layer: "Population Density" ← map_layers row, no group │ └── Map: "Shared Base" ← maps row, folder_id = NULL (root-level) ├── Layer: "Roads" └── Layer: "Topography"
Key distinction: Folders are workspace-level organizers for maps. Map Groups are inside a map and organize layers within that map. These are two separate tables with different purposes.

1.2 Where Permissions Are Stored

All permissions go into the resource_permissions table. There is one row per (user/group, resource) pair. There is no permission hierarchy — each row is explicit. Here is what the permission rows would look like for the example above:

who_user_id / who_group_idresource_typeresource_idrole_levelWhy this row exists
aliceworkspaceIsrael Survey OrgADMIN 4Alice owns the workspace
bobmapNorthern Survey 2025EDITOR 2Bob can edit features in this specific map's layers
field-team (group)layerSurvey PointsEDITOR 2All members of field-team can edit survey points
carollayerRoadsVIEWER 1Carol can read roads but not edit them
davemapShared BaseVIEWER 1Dave can open the embedded map when it's referenced
No cascade at query time. If Bob is EDITOR on "Northern Survey 2025" (a map), that does NOT automatically make him an editor on its layers. The frontend UI uses group permission grants (POST /maps/{id}/groups/{gid}/permissions) to create individual layer permission rows in bulk — but those rows are still stored individually in resource_permissions.

1.3 Embedded Maps

A map group can embed another map as its content. This lets teams reuse a curated base map without duplicating layers. Here is how it looks at the DB level:

maps table: id = "shared-base" name = "Shared Base" id = "southern-map" name = "Southern Survey 2025" map_groups table: id = "embed-group-1" map_id = "southern-map" ← belongs to the parent map embedded_map_id = "shared-base" ← this is what makes it an embedded-map node name = "Shared Base" ← display name, copied from embedded map on create parent_id = NULL ← top-level in the parent map's tree map_layers table: → NO rows link "southern-map" to the roads/topography layers directly. → Layers are resolved dynamically from "shared-base" at query time. → Permissions are checked against "shared-base" (the embedded map), not "southern-map".
Circular reference protection: The DB has a CHECK constraint preventing self-embed (embedded_map_id != map_id). The API's _check_embed_cycle() function walks the embed chain before inserting to catch deeper cycles (max depth 5).

Section 2 — Database Schema

All tables below live in the geo_meta database unless marked (shard DB). The features table lives in geo_features and is partitioned. Migrations use Alembic with two independent branches (meta and features).

resource_permissions

Central permission table. One row = one (subject, resource, role) grant. No deny rules. MAX(role_level) wins when multiple rows match a user via group membership.

ColumnTypePurpose
idUUID PKPrimary key
who_user_idUUID → usersDirect user grant; NULL if this is a group grant
who_group_idUUID → groupsGroup grant; NULL if this is a user grant. Exactly one of these is non-null.
resource_typeTEXT NOT NULLworkspace / folder / map / layer
resource_idUUID NOT NULLThe specific workspace/folder/map/layer being granted access to
role_levelINT NOT NULL1=VIEWER, 2=EDITOR, 3=MANAGER, 4=ADMIN. Numeric so MAX() resolves conflicts.
granted_byUUID → usersWho created this permission row
granted_atTIMESTAMPTZWhen granted

Constraint: CHECK ((who_user_id IS NULL) != (who_group_id IS NULL)) — exactly one of user/group must be set.

resource_versions

Stores the full state snapshot of a resource at each version. Full snapshots, not diffs — this means you can view or restore any version in O(1) without replaying N patches.

ColumnTypePurpose
idBIGSERIAL PKMonotonically increasing row ID (not version number)
resource_typeENUM(layer, map)Which resource type this version belongs to
resource_idUUID NOT NULLWhich specific layer or map
versionINT NOT NULLVersion number within this resource, starting at 1. Generated race-condition-free by next_resource_version() using FOR UPDATE.
snapshotJSONB NOT NULLFull state of the resource at this version (name, description, schema, status, tags, etc.). Not a diff.
changed_fieldsTEXT[] NOT NULLList of field names that changed from the previous version (e.g. ["name", "status"]). Used to display what changed in the version list UI.
messageTEXTOptional user comment. Set to "Restored from v{N}" on restore.
changed_byUUID → usersWho made this change
changed_atTIMESTAMPTZWhen the change was made
Race-condition-free version numbering: The SQL function next_resource_version(type, id) uses SELECT MAX(version) ... FOR UPDATE within the same transaction as the resource UPDATE. This prevents two concurrent edits from getting the same version number.

saved_expressions

Named reusable filter expressions scoped to a layer. The expression field stores a compiled DSL tree that is passed directly to compile_expression().

Section 3 — Permission System

Role Levels

LevelNameWhat they can do
1 — VIEWERViewerRead features, view styles, download exports (if export permission set), open maps
2 — EDITOREditorAll of VIEWER + create/edit/delete features, upload styles, use expressions
3 — MANAGERManagerAll of EDITOR + grant VIEWER/EDITOR to others, manage layer schema, lock/unlock layers
4 — ADMINAdminAll of MANAGER + grant MANAGER/ADMIN, delete maps/layers, manage workspace settings
∞SuperadminGlobal bypass — all checks return true. Set on the User row, not in resource_permissions.

Resolution Logic

When checking if a user can perform an operation on a resource:

1. Is user superadmin?
→ ALLOW
→
2. Get user's groups
(Redis cache, then CTE)
→
3. Query resource_permissions
WHERE resource_id = ? AND
(who_user_id = ? OR who_group_id IN (?))
→
4. MAX(role_level) wins
0 rows → DENY
→
5. Compare to required level
VIEWER=1, EDITOR=2, etc.

There is no cascade — a workspace permission does NOT automatically grant access to maps or layers inside it. The frontend uses the bulk-grant helper to create individual rows.

Embedded Map Permission Logic

When resolving GET /maps/{id}/open and a group has embedded_map_id set:

  1. Check user has VIEWER+ on the embedded map (not the parent map)
  2. If no access → node appears as {"type":"embedded_map","access":false,"children":[]}
  3. If access → recursively resolve the embedded map's tree with the same per-layer permission checks
  4. Layer-level permissions inside the embedded map are still checked individually — having viewer on the embedded map is only a gate, not a grant on layers
  5. Max embed depth: 5 levels (enforced in map_service._check_embed_cycle())

Section 4 — Change Tracking & Freshness

New Columns on layers (migration 009)

The existing updated_at conflates metadata changes (name, schema) with data changes (features edited). These new columns separate the signals:

ColumnUpdated whenUsed for
updated_at (existing)Name, description, schema, status, tags changedMetadata version list; ArcGIS layer refresh
updated_by (new)Same as updated_atVersion history attribution ("Alice changed schema")
features_updated_at (new)Any feature mutation (geom OR properties changed, or deleted)Map freshness endpoint; Argo delta sync optimization
features_updated_by (new)Same as features_updated_atFreshness response ("Bob edited a feature 2h ago")

Mutation Flow — What Happens After Every Feature Write

All four mutation endpoints (create, update, delete, bulk-delete) call these in order after commit, all fire-and-forget:

Feature write
committed to DB
→
refresh_layer_geometry_types()
(only if geom changed)
→
refresh_layer_bbox()
(only if geom changed)
→
refresh_layer_feature_stamp()
(always — even for properties-only edits)
→
refresh_map_content_for_layer()
(asyncio.create_task — background)
Bug in current code (features.py:206): update_feature() only calls refresh_layer_geometry_types() when body.geom is not None. A properties-only edit (changing a field value but not the geometry) produces zero change signal — features_updated_at is not updated, maps don't know the layer changed. The fix is to call refresh_layer_feature_stamp() unconditionally on every mutation.

Freshness Endpoint

GET /maps/{id}/freshness?since=<ISO-timestamp> — answers "has anything in this map changed since X?"

{
  "map_id": "...",
  "content_version": 12,
  "content_updated_at": "2025-01-15T10:30:00Z",
  "any_change_since": true,
  "changed_layers": [
    {
      "layer_id": "...",
      "name": "Roads",
      "features_updated_at": "2025-01-15T09:00:00Z",
      "features_updated_by": { "id": "...", "name": "Bob Cohen" },
      "metadata_updated_at": "2025-01-14T12:00:00Z",
      "metadata_updated_by": { "id": "...", "name": "Alice Levi" }
    }
  ]
}

The response is cached in Redis (mapfresh:{map_id}, 30s TTL). Invalidated when any feature mutation fires refresh_map_content_for_layer().

ETag on GET /maps/{id}/open: Built from "{map_id}-{content_version}-{unix_ts_of_max_features_updated_at}". Clients send If-None-Match → 304 if nothing changed. Eliminates full tree assembly + permission resolution on repeat opens.

Section 5 — Expression DSL

DSL Structure

Expressions are JSON trees with two node types: boolean combinators (AND/OR) and leaf conditions.

// Leaf condition — simplest form
{ "field": "status", "op": "eq", "value": "active" }

// Boolean combinator — nested AND/OR
{
  "op": "AND",
  "conditions": [
    { "field": "status", "op": "eq", "value": "active" },
    {
      "op": "OR",
      "conditions": [
        { "field": "population", "op": "gt", "value": 1000 },
        { "field": "area_km2", "op": "between", "lo": 10, "hi": 100 }
      ]
    }
  ]
}

Supported Leaf Operators

opSQL generatedNotes
eqproperties->>:f = :vString equality
neproperties->>:f <> :vNot equal
gt / gte / lt / lte(properties->>:f)::numeric > :vNumeric comparison; value cast to numeric
between(properties->>:f)::numeric BETWEEN :lo AND :hiRequires lo + hi keys instead of value
containsproperties->>:f ILIKE :vValue auto-wrapped in %…%
starts_withproperties->>:f ILIKE :vValue gets % suffix
ends_withproperties->>:f ILIKE :vValue gets % prefix
inproperties->>:f = ANY(ARRAY[...])Value must be array
not_inproperties->>:f <> ALL(ARRAY[...])Value must be array
is_nullproperties->>:f IS NULLNo value key needed
is_not_nullproperties->>:f IS NOT NULLNo value key needed

Security Model

The compile_expression() function in services/feature_filter.py is the sole entry point. It enforces:

  • No string interpolation: Field names go as values to properties->>:f_N, never into the SQL string itself. All values go through the named params dict.
  • Allowlist ops: Any op not in the frozen set → immediate ValueError → 400 response. Unknown ops like "raw_sql" are rejected.
  • Schema validation: Field names are validated against the layer's json_schema.fields set. An unknown field → 400. This is the primary injection surface — it's eliminated by using params, not format strings.
  • Depth limit: Max 10 levels of nesting; max 50 total conditions. Protects against stack overflow.

Section 7 — Caching Strategy

Redis is configured but currently unused. The biggest performance win is caching _resolve_custom_group_ids() which runs a recursive CTE on every authenticated request.

Performance impact: Before caching, a typical authenticated feature request makes 5 DB round-trips (JWT decode + user SELECT + last_seen UPDATE + recursive CTE + permission check). After caching: 1 DB round-trip + 2 Redis ops (~0.2ms each vs ~3ms per DB query on pgbouncer).

Section 9 — Identify Layers by Polygon

Concept

The user draws a polygon on the map. The system returns all accessible layers — including those with zero features in the area — organized in the existing group-layer folder hierarchy. Each layer is annotated with how many features it has inside the polygon. The user then picks which layers to load.

This is distinct from a regular spatial filter: it shows the full picture (including empty layers) so the user knows what data exists in the area, not just what matches. Layers with 0 features are shown dimmed in the UI but are still selectable.

User draws polygon │ ▼ POST /layers/identify { database_id, geometry } │ ├── Load all non-deleted layers for database ├── Filter to layers user has VIEWER+ on ├── Group by shard_id └── For each shard → one SQL query: SELECT layer_id, COUNT(*) FROM features WHERE layer_id = ANY(:ids) AND deleted_at IS NULL AND ST_Intersects(geom, ST_SetSRID(ST_GeomFromGeoJSON(:geom), 4326)) GROUP BY layer_id │ ▼ Assemble tree using group_layer_id folder hierarchy │ ▼ All accessible layers with feature_count_in_area (count=0 for layers with no features inside polygon — still shown)
Why one query per shard, not one per layer: Using WHERE layer_id = ANY(:ids) with a GROUP BY runs a single query for all layers on the same shard. This is O(shards), not O(layers). For a typical database with 50 layers all on shard 0, this is one query total.

Response Shape

Uses the existing group_layer_id folder system on the Layer model — not map groups. Layers with no group appear at root level. When a map_id param is added in a future version, the map's group tree can be used instead.

Backend Implementation Notes

Route must come first: POST /layers/identify must be registered in routers/layers.py BEFORE any @router.get("/{layer_id}/...") or @router.post("/{layer_id}/...") routes. FastAPI matches routes top-to-bottom — if /{layer_id} appears first, the string "identify" is parsed as a UUID and the request fails with 422 before reaching the endpoint.

GeoJSON geometry validation:

GEOJSON_GEOMETRY_TYPES = frozenset({
    "Point", "MultiPoint", "LineString", "MultiLineString",
    "Polygon", "MultiPolygon", "GeometryCollection"
})
# Check before any DB access → 400 if geometry.type not in this set

Shard query:

SELECT layer_id::text, COUNT(*) AS cnt
FROM features
WHERE layer_id = ANY(CAST(:ids AS uuid[]))
  AND deleted_at IS NULL
  AND ST_Intersects(geom, ST_SetSRID(ST_GeomFromGeoJSON(:geom), 4326))
GROUP BY layer_id

Layers not in the COUNT result get feature_count_in_area = 0 — they still appear in the response. PostGIS parse errors are caught and re-raised as 400 with a clear message.
