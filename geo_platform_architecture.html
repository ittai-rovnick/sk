Scaling tiers — the core strategy

Same code, same schema, same API across all tiers. Only the config changes as you grow.

TierLayer countDatabase setupFeature shardsWhen to move up
Tier 1 0 – 5,000 1 metadata DB + 1 features DB (can be same instance) 1 shard (shard 0) When total features exceed ~50M rows or query latency exceeds 200ms
Tier 2 5,000 – 50,000 Dedicated metadata DB + 2–4 feature shards 2–4 shards When a single shard exceeds ~200M rows or CPU stays above 70%
Tier 3 50,000+ Metadata DB cluster + 8+ shards + read replica per shard 8+ shards Add shards as needed. No ceiling.

How a feature query flows through the system

Example: Argo requests all features in a bounding box for layer X

1. Argo sends GET /layers/{id}/features?bbox=…
→
JWT validated (no network call)
~0ms
2. Check permissions in metadata DB
→
can_user_do(user_id, layer_id, 'read')
~2ms (cached in Redis)
3. Get shard_id from layer metadata
→
layer.shard_id = 2
~1ms (cached in Redis)
4. Route to features shard 2
→
SELECT * FROM features WHERE layer_id=X AND ST_Intersects(geom, bbox)
~10–50ms (GIST index)
5. Return features to Argo
→
GeoJSON response
Total: ~15–55ms

Will it work well?

✓ Metadata DB stays fast no matter how big features grow.  Every permission check, layer list, and dashboard load hits only the tiny metadata DB. Feature shards never slow down metadata operations.
✓ Feature queries never slow down as you add more layers.  Every query includes layer_id, so PostgreSQL hits exactly one of 32 partitions. Adding 10,000 more layers doesn't affect query time for existing layers.
✓ Scaling from Tier 1 to Tier 3 requires zero code changes.  You add shards to the config file and run a migration script that moves data. The API routing logic never changes.
✓ Argo offline sync is isolated per shard.  Argo's selected layers live on known shards. Syncing doesn't affect other shards or other users.
✓ Mixed layer sizes (5 rows to 500,000 rows) are handled identically.  A 5-row layer is just 5 rows in one partition. A 500,000-row layer is 500,000 rows in one partition. Same indexes, same queries, same speed.
! One known risk: metadata DB is a single point of failure.  If it goes down, everything stops. Mitigate in production with a hot standby replica. Not needed for local development.
